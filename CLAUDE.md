# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It is meant to be public: "the maintainer" is the project's author, and decisions marked as the maintainer's are not to be changed without asking. Private notes, paths to local source material, details of the maintainer's physical machines and legal or strategic considerations belong in the gitignored `CLAUDE.local.md`, never here.

## Project

**Wolf80** (the name, with the subtitle "emulator of Czechoslovak single-board computers", Czech "emulátor československých jednodeskových počítačů"; the maintainer's decision, 2026-11-01) is an emulator of two Czechoslovak educational single-board computers: **PMI-80** (Intel 8080 compatible MHB8080A, 1982) and **Savia-84** (Z80/U880), and of the **Stone 1**, a modern cross of the two by Radek Veselý. It has its own **i8080 and Z80 cores**: the 8080 core (`src/core/i8080.js`, mnemonics and disassembler in `i8080-disasm.js`) and the Z80 core (`src/core/z80.js`, `z80-disasm.js`); the boards (`src/board/pmi80.js`, `savia84.js`, `stone1.js`, with `src/machine/i8255.js` and the multiplexed display `src/machine/display.js`), described for the UI by `src/board/profiles.js`; the web UI (`src/ui/`) with sound from the tape output K3 (a virtual amplifier, `src/machine/audio-render.js`, `src/ui/audio.js`) and a two-pass 8080 assembler (`src/asm/asm8080.js`, Intel syntax, TASM-compatible enough to rebuild TENIS byte for byte); and the desktop EXE (`desktop/wolf80_desktop.cpp`, a C++ wrapper around WebView2 as in SFMT, built by `tools/build-desktop.mjs`, see `docs/desktop.md`). Planned work is in `docs/TODO.md`. How the boards are modelled, with the certainty of every fact, is in `docs/pmi80.md`, `docs/savia84.md` and `docs/stone1.md`; checks that need a physical machine are queued in `docs/hardware-tests.md`.

## Commands

```bash
node tools/build.mjs                       # dist/web + dist/Wolf80-offline.html (after every change in src/, programs/, roms/)
node tools/build.mjs --with-sources        # the same, with the demo programs' sources embedded (off by default, see programs/README.md)
node tools/serve.mjs 8780                  # serves dist/web on 127.0.0.1:8780 (launch config "wolf80-web" in .claude/launch.json)
node tools/build-desktop.mjs                # dist/desktop/Wolf80.exe (needs the toolchain, see docs/desktop.md)
node tools/make-listings.mjs                    # Intel HEX and a byte list beside every demo program source and binary and every extras/ source (--check: only compare)
node tools/make-icon.mjs                   # EXE icon assets/icon/wolf80.ico (16–256 px) + preview docs/img/icon.png
npm test                                   # all unit tests (node --test "tests/*.test.mjs")
node --test tests/i8080.test.mjs           # one test file
node --test --test-name-pattern="DAA" tests/i8080.test.mjs   # one test
node tools/cpu-exercise.mjs third_party/cpu-tests/TST8080.COM # a CP/M CPU test program
node tools/cpu-exercise.mjs --z80 third_party/cpu-tests/zexall.com  # the Z80 exerciser (ZEXDOC, ZEXALL)
```

`site/` holds files served only beside the web version on GitHub Pages (the Google Search Console verification file, `sitemap.xml`); `.github/workflows/pages.yml` builds the latest release tag reachable from `main`, adds them and deploys, at each tag push or by hand. Releases: EXE, ZIP and `Wolf80-offline.html` are built locally from the clean tagged tree and attached to the GitHub release.

The CP/M CPU test programs (TST8080, 8080PRE, CPUTEST, 8080EXM; ZEXDOC and ZEXALL for the Z80) are third-party files kept only locally in the gitignored `third_party/cpu-tests/` (source in `third_party/README.md`). `tools/build.mjs` bundles the modules listed in its `MODULES` array (in dependency order) into one IIFE: imports and exports are stripped, so top-level names must be unique across all modules (the build checks it). The ROM and the demo programs are embedded as `globalThis.WOLF80_ASSETS`. The built-in browser shows a `file://` page only as a static snapshot; check the UI through `tools/serve.mjs`. For a sharp full-size screenshot, headless Edge works: `msedge --headless=new --window-size=1920,970 --virtual-time-budget=1500 --screenshot=<png> http://127.0.0.1:8780/#ladeni` (the hash opens a work-area tab: `tahak`, `instrukce`, `ladeni`).

**Demo programs** are data, not code: `programs/catalog.json` lists them in display order (board and optionally the firmware they run on, file, format `ihex`/`bin`/`asm`/`rom`, load and start address, author, Czech and English help); origin and SHA-256 of each file go into `programs/README.md` (a test checks it). One folder per program, one file per board (`programs/bagels/bagels-savia.asm`); beside every `.asm` and `.bin` an Intel HEX (`<name>.hex`) and a list of bytes to type in by hand (`<name>-bytes.txt`), made by `node tools/make-listings.mjs` (run it after changing a program; a test fails when one is out of date), so programs can be handed out and entered into real boards without the emulator (the maintainer, 2026-10-27). **The builds embed the assembled programs, not their sources** (the maintainer's decision, 2026-10-29): for an `asm` entry `tools/build.mjs` (`tools/program-assets.mjs`) embeds the neighbouring `.hex` (and fails if it does not match the source); `node tools/build.mjs --with-sources` adds each source, gzipped, as an optional `source` field. Do not switch the sources back on, or suggest it, unless the maintainer asks or the work is the in-app source view or the development environment; why they were embedded before, why not now and what they may be good for later is in `programs/README.md` ("Sources in the builds"). A program is started by typing the monitor's run command on the emulated keyboard (`pmi80RunKeys`: `= EX addr =`; `savia84RunKeys`: `Ex addr dA`), so the monitor's state is as after a real start; COSMOS, for example, relies on the display pointer the monitor sets.

**Extras** (`extras/`, the maintainer's decision, 2026-10-29): small programs to try on the emulated and the real boards, distributed with the source for interest but not part of the emulator: not in `programs/catalog.json`, not in the builds. One folder per program, one source per board or monitor (`extras/clock/clock-pmi80.asm`, `-pmi80c` for the PMI-80 C monitor); each is a commented `.asm` whose header carries the instructions for use (a README in the folder only when the header is not enough), with the Intel HEX and byte list beside it from `node tools/make-listings.mjs`, which assembles every `.asm` under `extras/`. `extras/README.md` describes the collection and lists its programs (add a row for each new one); tests are in `tests/extras.test.mjs`. Programs by other authors name author and source, as in `programs/`.

8080EXM takes about 70 s (23.8 billion states; all 25 groups passed on 2026-10-18); run it only after a change to the 8080 core. ZEXDOC and ZEXALL take about 160 s each (all 67 groups passed on 2026-10-24); run them only after a change to the Z80 core.

**Language:** the repository is **English**: code, comments, tool messages, docs, `CHANGELOG.md`, this file and commit messages. The user interface is **English with a Czech switch** at the bottom of the side panel, remembered per browser (the maintainer's decision, 2026-10-19; most users are Czech and Slovak); before any choice, a browser set to Czech or Slovak opens in Czech, any other in English (the maintainer, 2026-11-01). All UI texts live in `src/ui/i18n.js` (an `en` and a `cs` catalogue, English is the fallback); `index.html` names them with `data-i18n`, `data-i18n-html`, `data-i18n-title`, `data-i18n-placeholder` and `data-i18n-aria`, the code calls `t(key, params)`. Never write a user-visible string straight into the HTML or JS; `tests/i18n.test.mjs` checks that both catalogues match and every used key exists. SFMT is to get the same approach. The case's wordmark (the board's name) stays as it is; the subtitle beside it (JEDNODESKOVÝ MIKROPOČÍTAČ / SINGLE-BOARD MICROCOMPUTER, on two lines) is translated (the maintainer's decision, 2026-10-19). The demo programs keep their names, except the project's own Czech-named ones, which have English names too (Mikrovarhany / Micro Organ, Světelný had / Light Snake; the maintainer, 2026-10-26); in `programs/catalog.json` a name, an author and the help are a text or `{ cs, en }`.

**Technology** (the maintainer's decision), the same as the maintainer's sibling SFMT emulator:
- plain ES modules with no third-party packages, Node.js ≥ 20,
- `tools/build.mjs` joins the modules into one IIFE and produces a static web site and a single-file offline HTML,
- the desktop version is a single EXE: a custom C++ wrapper around WebView2, built with llvm-mingw. The toolchain path is configurable (it lives outside the repository); nothing else in the build may depend on files outside the repository.

**Architecture open to the future** (the maintainer's decision): the layers are CPU core → machine (board, memory map, I/O, time) → debug API → UI, and the UI never reaches into the core directly. The debug API (read/write memory and registers, 8255 port state, stepping, breakpoints, watches, disassembler) is designed from the start as a separate layer: panels for viewing and editing memory, inputs and outputs and debugging will be built on it, and later a **development environment for 8080/Z80** in the context of both boards (editor, assembler, assembling straight into the emulated memory).

**Firmware:** the default and preferred firmware is the **factory monitor** of each board (original PMI-80, original Savia; on the Stone 1 its own monitor, withheld for now, see `docs/stone1.md`). A firmware is a choice within a board, not a separate computer: PMI-80 C (by Nostalcomp, with the maintainer's scrolling text and its second EPROM with the games) is the PMI-80's second monitor; Nostalcomp's STONE-PMI is the Stone 1's second monitor (the maintainer, 2026-10-26).

**License:** GPL-3.0-or-later, as the maintainer's microHAMCLOCK; `LICENSE` is the verbatim GPL-3.0 text. Every hand-written source file starts with an `SPDX-License-Identifier: GPL-3.0-or-later` line and the copyright line `Copyright (C) 2026 Matěj "Wolf" Holyszewski`. No outside code without the contributor's agreement to `CLA.md` (version 1.0, modelled on microHAMCLOCK's; `CONTRIBUTING.md` says how), and no third-party GPL code without asking the maintainer.

**ROM images and third-party programs are published** with the emulator (the maintainer's decision, 2026-10-20): the factory ROMs, derived ones such as Nostalcomp's, and demo programs by other authors (COSMOS, TENIS…). They are not the maintainer's work, so they stay outside the project license, in their own folders (`roms/`, `programs/`) with a note on their origin. **Be transparent:** everything that is not the maintainer's work names its author (when known) and its source, with a link, in those notes and in "About the emulator" in the UI; Nostalcomp is credited for what it preserved, transcribed or modified.

**Physical hardware:** work as theoretically as possible (documentation, ROM analysis, tests in the emulator). Tests on the maintainer's physical machines are collected in one list (in `docs/`, to be created) and requested in batches, or only when unavoidable.

## Build and test policy (the maintainer's decision)

Save time and tokens; never "everything after every change".
- **After a code change:** only the tests of the affected part (`node --test` on the specific file).
- **After a UI change:** build the web version and look at it in the built-in browser.
- **Offline HTML, EXE and browser checks:** only at the end of a stage, before a release, after a change to the build or the desktop wrapper, or when the maintainer asks.
- **Long CPU exerciser tests:** only after a change to a CPU core.

## Versioning

Versions are `x.y.z`. The first public release is **1.0.0** (the maintainer's decision, 2026-11-01: the emulator itself is complete; the development environment and the like are new features for later versions). From then on `z+1` for fixes only, `y+1` for features, `x+1` only when the maintainer decides; before it the versions were `0.x.y`. **The number changes only at a release, and only when the maintainer says so.** Between releases nothing is numbered by hand: a development build derives its version from `git describe` (e.g. `0.1.0+3-g1a2b3c4`, plus `-dirty`), and every change goes into the `## Unreleased` section of `CHANGELOG.md`. Never hardcode the number in the source. A release: the `## Unreleased` items move under `## X.Y.Z – date` (a new empty `## Unreleased` stays above), that is committed as "Release X.Y.Z" and tagged with an annotated tag `vX.Y.Z`; then, from the clean tree, `npm test`, `node tools/build.mjs` and `node tools/build-desktop.mjs`, and the builds show exactly `X.Y.Z`. The first release `0.1.0` was made on 2026-10-20 (the factory PMI-80 monitor running in the UI).

## Hardware facts that shape the architecture

Details and sources are in the project knowledge base outside the repository (see `CLAUDE.local.md`); whatever the implementation relies on is to be written into a specification in `docs/`.

- **Profiles, not hardcoding.** PMI-80: MHB8080A at ~1.111 MHz (10 MHz crystal, MH8224 divides by 9). Savia: Z80/U880 at 2 MHz (the schematic's 4 MHz crystal divided by two; the maintainer's board has a 2 MHz crystal without the divider, the same clock); the book allows other crystals. Stone 1: Z80 at 2 MHz. A machine profile holds the CPU, clock, ROM, memory map, digit select polarity and key labels.
- **The PMI-80 CPU is the TESLA MHB8080A**, a clone of the Intel 8080A (the maintainer's decision: Intel 8080 documentation is the reference, checked against any known MHB8080A differences, which are to be documented in `docs/`).
- **i8080 and Z80 are two cores**, not one extended core: flags (P/V, H, N), timing and undocumented opcodes differ. STONE-PMI contains the Z80 instruction IM 1.
- **Memory.** PMI: ROM 0000–03FF, optional EPROM 0400–07FF, RAM 1C00–1FFF, 2000–3FFF mirrors the lower 8 KiB, from 4000h the decoder is blocked. Savia: ROM 0000–03FF, RAM 1800–1FFF, A15 ignored (mirrors from 8000h); the emulator also has Nostalcomp's simplified decoder (2716 at 0000–07FF), not the default. Stone 1: ROM 0000–07FF, RAM 1800–1FFF, full decoding. An unpopulated address returns the last value on the data bus (measured on the PMI-80 and the Savia).
- **I/O.** The system 8255 is at F8–FBh (PA, PB, PC, CWR); PMI has an optional second one at F4–F7h. Port decoding is incomplete (PMI: any upper nibble; Savia and Stone 1: only A2=0), so ports have aliases. At start PMI writes CWR 8Ah, Savia 88h.
- **Display.** 9 digits; PA0–6 are segments a–g, active low; PA7 is not a segment (tape on PMI). The digit is selected by the low nibble of PC: PMI and Stone 1 `(~index)&0Fh`, Savia `index` (through a 74145). The display is multiplexed: the picture and its brightness come from the timing of writes to PA/PC, not from a buffer in RAM, so cycle-exact timing is required. Both factory ROMs scan 10 times (E=0..9) for 9 positions; PMI-80 C leaves the last digit lit longer (brighter). ROM behaviour is emulated faithfully, never "fixed".
- **Keyboard.** PC4–6 are inputs, a pressed key reads 0; columns are selected by the same decoder as the display digits (a 3×9 matrix). RE (and I on PMI) are wired to hardware (reset, interrupt), outside the matrix. PMI layout, 5×5:

  ```text
  RE  I  EX  R  BR
   C  D   E  F   M
   8  9   A  B   L
   4  5   6  7   S
   0  1   2  3   =
  ```

  Savia has the same functions with other labels (Ad/dA/minus instead of M/=/S, depending on the monitor).
- **Tape.** Only the factory PMI monitor has it (PA6 burst, PA7 data, input PC7, ~5 kHz). PMI-80 C has none; in the factory Savia ROM, LOAD/SAVE point into an unfilled FFh area.
- **Savia with eight digits.** The factory Savia ROM drives 9 digits and shows SLAVIA 84, but the book builds the board with 8: output 1 of the 74145 has no digit, so it reads SAVIA 84. The emulator shows 8 by default, as in the book, with an option for 9 (the maintainer's decision, 2026-10-26; his own board has 9).

## GUI (the maintainer's decisions)

- **Stylized skeuomorphism:** the UI resembles the real machine, but with flat colours and simple outlines; **no photorealism**, textures, gradients, shadows or imitated materials. The PMI-80 is shown in a **yellow plastic case**. The keyboard closely follows the real colour scheme (dark grey hex keys, blue function keys, light grey frame). Two exceptions chosen by the maintainer (2026-10-19): the keycaps show their bevel as flat bands (a light strip on top, a dark one at the bottom, no blur), and the grey panel has the outline of the real one (notches with their own pitch, sharp top corners, rounded bottom corners, a square tab from the middle of key 1 to the middle of key 3). The bubble LED display is not imitated; the digits are enlarged and readable.
- **Layout** as in SFMT, from right to left: the application control panel; next to it the display and keyboard (always visible); further left a switchable work area: the **Tahák** ("cheat sheet": monitor commands, services, scratchpad, memory map), **Instrukce** (a clean 8080 opcode table, like the one on the real case lid, without its block diagram, which is not wanted in the UI), debugging, later a board view or the development environment. All boards share the same UI and the size of the computer (the maintainer, 2026-10-26): the PMI-80 layout with relabelled keys, the board's name in the header at the same height (a long name is narrowed, never made smaller); the Savia can also have the arrangement of the maintainer's board ("4×6 – Wolfova Savia-84"), with keys of the same size and the spacing and edges of the PMI-80 layout, on a wider and lower panel centred in the same space (the maintainer, 2026-10-26).
- **The page always fits the browser window, never a horizontal scroll bar** (the maintainer's decision; a laptop with a low vertical resolution must work): the computer panel is drawn at a fixed design size and scaled as a whole (`fitCase` in `src/ui/app.js`, at most 1.2x), the work area takes the remaining width (at least 320 px), and only the panels scroll vertically. Check new UI at 1366×768 and 1920×970 at least.
- **Small screens** (the maintainer's decision, 2026-10-20; the breakpoint follows SFMT and may change): in a window narrower than 900 px or lower than 500 px (`setLayout` in `src/ui/app.js`, chosen by size, not by detecting a phone) the side panel becomes the first work-area tab, **Ovládání** (Controls), and the whole page scrolls vertically (still never horizontally). Portrait: the computer on top, fitting the window, the work area under it. Landscape: the computer on the left, the work area on the right; the whole computer fits the window height, and when that would make the keys too small (a phone on its side) the part from the display down fits it and the computer sticks to the top of the window. Check such changes at 375×812 and 844×390 as well.
- **Light and dark theme** (the maintainer's decision, 2026-10-21): buttons Světlý / Tmavý / Podle systému under the language switch, **dark by default**, remembered per browser (`applyTheme` in `src/ui/app.js`, an inline script in `index.html` sets a light theme before the first paint). **Only the page around the computer changes** (the panels' tokens under `:root[data-theme="light"]` in `style.css`); the case, board, display and keyboard keep the colours of the real machine. Panel rules use the panel tokens (`--heading`, `--value`, `--hl` …), never the computer's (`--case`, `--cream`).
- **Samsung Internet** recolours pages in its dark mode whatever they declare; a workaround for the display, limited to that browser at the maintainer's wish, is described in `docs/TODO.md` (Known behaviour).
- Display: unlit segments only faintly visible, lit ones bright with a slight glow (the maintainer's request).
- The opcode reference shows the code next to the mnemonic (with bytes and states), sorted by code or by name, with a search field; the 16×16 grid is only an extra view (the maintainer found the grid hard to read).
- Memory is shown as a scrollable hex view of the whole address space with a go-to-address field and ROM/RAM/unpopulated areas told apart by colour, never as a fixed small block.
- No manufacturers' logos in the UI or the builds, the TESLA logo of the real board included (the maintainer's decision, 2026-11-01); naming a manufacturer in the text is fine. The brand element is the wordmark from the "retro graphics" mockup: a heavy cream **PMI-80**, a thin vertical bar, the spaced caps subtitle on two lines (**JEDNODESKOVÝ MIKROPOČÍTAČ**, translated to **SINGLE-BOARD MICROCOMPUTER** in English), and a yellow rule underneath (the maintainer's decision).

## Rules

- A ROM running in the emulator, or passing tests, is not a verification of a physical board or of a particular EPROM. Distinguish documentation, ROM analysis, emulator behaviour and a test on a physical machine.
- Never determine a ROM or a clock from a board or file name alone; identify ROMs by SHA-256.
- Everything in the repository (code, comments, docs, commit messages) must be publishable.
